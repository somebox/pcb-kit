# How a hardware project is laid out and documented

What the existing projects converged on (dodeca-v2-hardware, rp2354-messages-sign, siebenuhr controller-v2,
rgb-spotlight), written down so new ones start the same way. `templates/project/` has the skeleton.

## Layout

```
README.md            index: what the project is, where things are, naming of versions
DESIGN.md            requirements, decisions (dated, numbered), block designs, what the last version taught
LAYOUT.md            the PCB: floor plan, stackup and rules, scripted copper, routing, checks, silkscreen
PRODUCTION.md        how to order: checklist (polarity, rotations), bring-up, costs; its overview is generated
CHANGELOG.md         what changed in each board version and why, newest first, citing DESIGN.md's decisions
pcbkit.toml          the project's settings for pcbkit release and production (templates/project has the defaults)
BOM.md               from bomi
boards/<name>/       one KiCad project per board (<name>.kicad_pro/.kicad_sch/.kicad_pcb, fp-lib-table)
lib/                 the project's own symbols (<project>.kicad_sym), footprints (.pretty), 3dmodels/
scripts/             the project's generators and checks; they call pcbkit for the shared parts
design/              block definitions (JSON) when the schematic is generated
docs/previews/<board>/   generated by `pcbkit previews`: schematic.pdf, pcb-front/back.png, assembly-back.png, board.pdf, renders
docs/datasheets/     bomi datasheet summaries (markdown), the PDFs where licensing allows
docs/overview.html   the project on one page for the user, a round added after each major design round (below)
docs/overview/       its rounds, r1.toml, r2.toml, ..., and img/, their pictures as they were (`pcbkit overview`)
docs/reviews/        failure reviews and failure analyses, dated (`<date>-<board>.md`)
releases/<board>/    releases.toml and v<version>/ per release: Gerbers, BOMs, placement files, PDFs, kicad/ (committed)
production/          orders/<date>-<what>/order.toml (and its ORDER.md), stock.toml, boards.toml (written by release)
build/               scratch fab files and panels, git-ignored
archive/             earlier versions, kept whole
```

**A series of boards** (synth-blocks: dozens of small boards of a few kinds) groups the boards by kind and keeps each
board's files together: `<kind>/<name>/` in place of `boards/<name>/`, with `previews/` and `fab/` inside the board's
folder (each release in `fab/v<version>/`) in place of `docs/previews/<board>/` and `releases/<board>/`: its
pcbkit.toml sets `release.dir = "{folder}/fab{sub}"` and `previews_dir = "{folder}/previews{sub}"`. Keep every board
folder two levels below the root, so the `${KIPRJMOD}/../../lib/` paths that `pcbkit new` writes into its lib tables
and 3-D models still hold. The project's AGENTS.md says it does this, since the skills default to `docs/previews/`.

## Writing

- The first line under a document's title is its **status with a date**: what is done, what is next.
- Decisions are **dated and numbered** (D1, D2, ...) in DESIGN.md and never silently rewritten; a reversal is a new
  entry that names the old one.
- Positions are in board coordinates, millimetres, top view; say which side a part is on.
- Every generated artefact says what made it (`pcbkit previews`, `scripts/make_fab.sh`) so it can be regenerated.
- The order checklist in PRODUCTION.md is the list of things that went wrong before (polarity, rotation, BOM matching
  by value), each with the fix.
- **A prototype says so.** DESIGN.md's requirements name the build as a prototype or a product. For a prototype
  they give the conditions it will be used under: the supply, exactly (its voltage, its current limit, the one
  adapter), and how it is handled on the bench. A risk those conditions hold (the wrong adapter, a hot-plug, a
  reversed plug) is noted, on the silkscreen where there is room and in PRODUCTION.md's bring-up section. The
  part that would remove it is listed in DESIGN.md for the revision that warrants it, and is not designed in yet:
  that is where a prototype saves its money.

## Versions, releases and orders

- A board's version is `major.minor.patch`, written "1.0.0" in the data and v1.0 (then v1.0.1) on the board. Only
  `pcbkit release` changes it. What changed since the last release says which part goes up:
  - **minor** when the circuit changed: the netlist or the BOM. A part added or removed, a part's footprint, value,
    LCSC or MPN field, DNP or exclude-from-BOM flag (a value alone counts), a pin on another net. Release reads them
    from the board, board-only footprints left out, and keeps their fingerprint in releases.toml (`circuit`). A net
    renamed is the same circuit.
  - **patch** when the netlist and BOM are the same and the fab output isn't: the layout changed.
  - **major** for a change that breaks what depends on the board: the header pinout between stacked boards, the
    outline or the mounting holes, the GPIO map the firmware relies on. Release can't tell those, so it is only ever
    `--major`.

  `--minor` and `--patch` override the choice, and `--dry-run` says which part it would bump and what changed
  ("R3 value 10k -> 4.7k", "net VIN gains U2.5"). A release recorded before pcbkit kept the circuit fingerprint has
  nothing to compare with: the next change gets a patch, and the output says why (`--minor` if the circuit changed).
  A board unchanged since such a release gets the fingerprint recorded on the next run.
- **The label.** `[release] label = "short"` (the default) writes v1.4, then v1.4.1 after a layout fix: the shortest
  text on the silkscreen, and the version as people say it. `label = "full"` writes v1.4.0 every time: for a
  project whose boards were labelled so before (ESP Candle's v1.3.1 and v1.4.0), for firmware or a test jig that
  reads the version back with three parts, or where patch releases are common and the label should keep one width.
  Choose before the first release: the label names the release folders (`v1.4/` or `v1.4.0/`), and changing it
  later leaves the earlier folders as they were named. Boards made to work together (a stack, a base and a top) can
  share one version when every change to one is released with the other (`--version` for both); otherwise each
  board has its own.
- **The version and date on the board are KiCad's text variables**, never typed in. Release stamps the title block
  of the board, of its root schematic and of every sheet under it in the board's folder that has a title block of
  its own (KiCad prints each sheet's own on its page of schematic.pdf; Page Settings' "Export to other sheets" gives
  them one), and gives the board and the root schematic each other's title and company when one has none. The
  silkscreen says `${REVISION}` and `${ISSUE_DATE}` (for example `${ISSUE_DATE} ${REVISION}`, or
  `<name>\n${REVISION}\n${ISSUE_DATE}` on the back), which KiCad fills from the board's title block when it plots
  the Gerbers, so the board text never changes and DRC measures what it will print. `${TITLE}` and `${COMPANY}` work
  the same. Two variables print wrong, and release refuses a board that has one on its silkscreen, copper or mask:
  `v${REVISION}`, which prints vv1.4 (the rev is the label, its v included), and `${CURRENT_DATE}`, which prints the
  day of the plot, so no two runs make the same Gerbers and the release can't be compared with. A version typed
  into a silkscreen text (`v1.4 2026-03-01`) is still stamped where it matches the old label and an ISO date, and
  release says so. Leave room on the silkscreen for the longest label (v1.0.10, v10.0) and date the format makes.
- **The date format.** `[release] date_format` is the title block's date, so `${ISSUE_DATE}`'s, as a strftime
  format: `"%Y-%m-%d"` (the default, 2026-11-15) sorts and reads the same everywhere; `"%m.%Y"` (11.2026) or `"%Y-%m"`
  is shorter, for a small board or a project that labelled its boards by month before. It changes only what is
  written: releases.toml keeps each release's date as a date, the fingerprints mask the title block, and a release
  compared with later is stamped with the date its own `kicad/` copy carries. A version typed into the silkscreen
  keeps its date in ISO.
- **A first release.** A board without releases takes the version its title block reads (its root schematic's
  when the board has none, as KiCad's blank board hasn't) only when that is a draft's (`0.1-draft` gives 0.1.0, as
  `pcbkit new` writes it in both) or there is none (1.0.0). A rev that is a version alone (`v1.4`, `1.3.1`, `2.0`)
  may be the label of boards already built, and if the circuit or layout has changed since, the new board would go
  out under the same label: release asks for `--version`, and says what git knows, the commit where the title block
  first read that version and whether the netlist and BOM have changed since (`pcbkit changelog` says how). Use the
  title block's own version when no board of it was built, else the next one: minor after a change to the circuit,
  patch after one to the layout only. ESP Candle's top read 1.4.0 as converted from the boards that were built, and
  35 netlist and BOM changes later went out as 1.5.0, with the base (from 1.3.1) as its matched pair.
- **CHANGELOG.md** at the project's root says what changed in each board version and why, newest first:
  - a section per version as released, `## <board> v1.1 (released 2026-11-20)`, or `## v1.5.0, both boards
    (released 2026-11-15)` for boards released together; a `### <board>, from v1.0` per board under it;
  - first what the version is for, and what it still works with (the pinout, outline, mounting and GPIO map
    unchanged: a v1.5.0 base still fits a v1.4.0 top);
  - one entry per change, grouped by block (power, USB, LEDs, layout, silkscreen), each citing the decision (D12) or
    review finding (F27) behind it. A change that needs something elsewhere says so: firmware, an enclosure, a
    different solder paste;
  - a line saying the entries were checked against what the boards say: every netlist and BOM change since the last
    release (or the board as built) is one of them;
  - `## Unreleased` on top while the next version is being made, which becomes its section at the release;
  - a closing section for the versions before the project used pcbkit, pointing at `archive/`.

  `pcbkit changelog` drafts it: what changed in each board since its last release (as its `kicad/` copy has it),
  since a board named (`--since archive/v1.3.1/board.kicad_pcb`, or a git commit or tag), or, for a board never
  released, since the commit where its title block first read its version. `--all` adds each release against the one
  before. Its lines are what changed; the changelog adds why. `--note` on `pcbkit release` is one line kept in the
  version's releases.toml entry, in place of the bump's reason: what the version is for, pointing at the
  changelog ("First KiCad version of both boards (CHANGELOG.md, D7-D30)"). releases.toml is written by release and
  never edited; CHANGELOG.md is written by people and agents.
- Generators that write a board read its version from its releases.toml rather than keeping their own.
- A release folder is never rewritten: what was ordered stays in git as it was sent. Beside the fab files and PDFs it
  holds `kicad/`, a frozen copy of the board's KiCad project: the .kicad_pro, every schematic sheet (one from outside
  the board's folder in `kicad/outside/`), the .kicad_pcb, the .kicad_dru and the library tables (not the .kicad_prl,
  lock files or `.history/`). Every released version opens in KiCad on its own, beside the working board or another
  release. Its symbols and footprints are embedded in the
  files; the paths in its library tables and 3-D models are rewritten to reach the same files from the release
  folder, so they show the project's `lib/` as it is now, not as it was. MANIFEST.txt lists what the copy names and
  doesn't find. The board itself stays one project in `boards/<name>/`, edited in place: the versions are the
  release folders.
- **A change during the release steps is a new release.** Once a board is released, anything that changes it (a
  fix from the checks before an order, a part swapped for stock, a rotation rule corrected) goes into the project
  and comes out as the board's next version: a patch when only the fab output changes, a minor when the netlist
  or BOM does. The order then pins that version. Nothing is edited in a release folder, and what is ordered is a
  release: its own files, or, for another split of the sides, the BOM and placement pair `pcbkit fab` makes from
  the board as released (`pcbkit release --dry-run` gives it no new version). Files for a quote alone need no
  release. Each such change repeats the order's steps, so the design is settled with the user first.
- An order is a folder under `production/orders/`, named by its date and what it is. Its order.toml pins each
  board's version and records what happened as dated events: draft, submitted (with the order number and price),
  in-production, shipped, received, problem (a stock shortage, a question from the fab), cancelled. Edit it by
  hand, or tell an agent what happened, then run `pcbkit production` and commit: git log of the order file is its
  history, and PRODUCTION.md's overview shows every board's version, state, orders and stock at a glance. A board
  that needs other fab settings than the order's (a front panel's black mask) says so in its own `fab`; parts
  bought with the order but not placed on a board (spare ICs, a rework kit) are `[[extra]]`s: part, qty, buy, note.
  Two drafts that are to ship together are merged into one order rather than one being cancelled.
- `production/stock.toml` counts boards by version (bare, assembled, built, tested) and the parts on hand for
  finishing them, by the names the overview uses.

## Checks before an order

1. A failure review (the failure-review skill) of the version being ordered, before the checks below, since the
   changes it leads to need them again: its briefing in `docs/reviews/`, the changes the user accepted as decisions
   in DESIGN.md, its test points on the board, its bench list in PRODUCTION.md under "Bring-up". Once those
   changes are made, a review of the changes at the commit to be ordered: a fix is a new design.
2. `pcbkit erc` clean, the project's netlist assertions pass.
3. `pcbkit drc --save` with 0 errors, 0 unconnected, 0 parity issues; warnings explained in LAYOUT.md. An error
   that is accepted (a vendor's footprint as it was built, two courtyards closer than KiCad's rule but farther apart
   than the assembler's minimum) is measured, then given a custom rule in the board's `.kicad_dru`: scoped to the
   part, its limit just under the value measured, its name and comment saying the part, the value, the rule it
   breaks and why that is accepted. ESP Candle's base, whose USB-C pads sit 0.244 mm from the connector's own
   pegs against 0.25 mm, as JLC built v1.3.1:

   ```
   # Hole clearance inside the USB-C footprint as fabricated on v1.3.1: pads B1 and B12 are 0.244 mm from the
   # connector's NPTH pegs, against the project's 0.25 mm. JLC built it so (D29).
   (rule "USBC1: pads B1/B12 0.244 mm from its own pegs, as fabricated"
     (constraint hole_clearance (min 0.24mm))
     (condition "A.memberOfFootprint('USBC1') && B.memberOfFootprint('USBC1')"))
   ```

   DRC then passes, and the part closer than the rule's limit, or any other part closer than the project's, is still
   an error. The rule is in the board's fingerprint and in each release's `kicad/` copy. A DRC exclusion would also
   clear it, but it is kept in the .kicad_pro as the marker (its type, items and place), says no value, and comes
   back when a part moves. Until then `pcbkit release` counts the board as a mockup and names the errors:
   `mockup (drc 2: 2 hole_clearance (USBC1))`.
4. `pcbkit check` with nothing unexplained; `pcbkit cleanup --dry-run` reports nothing.
5. A second opinion from KiCadRoutingTools' checkers (`check_drc.py`, `check_weird.py`, `check_connected.py`) on a
   copy of the board, for via-in-paste, stacked copper and near-open joints.
6. `pcbkit previews` regenerated and looked at: assembly map, silkscreen, plane coverage.
7. `pcbkit release` (which reruns ERC and DRC and refuses a board with errors), and `pcbkit panel` for panels; BOM
   reviewed against bomi for stock and extended-part fees; an order.toml pinning the released versions, then
   `pcbkit production`, which fills the order's `upload/` folder from the pinned releases.
8. The user confirms the versions to be ordered and that no design change is open. Nothing goes into a cart before
   that: the forms, the BOM page and the viewer are many steps, and a change after them means a new release and
   all of them again.
9. The order itself, last and once: the upload from the order's `upload/` folder. The fab-order skill covers the
   forms, the BOM page and the placement viewer, where every part in the release's placement checklist is checked
   before the order goes into the cart.

## The overview page

After each major design round (a review and its decisions, a re-layout, a release) the user gets the whole project
on one HTML page, `docs/overview.html`: brief, well organised, made to be used.

- **Status** first: the project's, then each board's version and state, and what is next.
- **A viewer** of the board or the product that the user can turn, or switch layers in.
- **A section per block or topic** (power, the MCU, the LEDs, the enclosure, firmware): a few lines and its state.
- **Open decisions**, each with its options and the one recommended.
- **Cost, supply and fab** in summary: the unit cost, parts low in stock, the fab options, the orders.
- **Rounds.** The page keeps every round and switches between them. A new round is added; the earlier ones stay
  as they were.
- **Status marks** are the same few throughout, explained by one legend.
- A small change is added to its round as a dated note. Sections are not rewritten for it.

The page is made from what the project already records (the status lines, DESIGN.md's decisions, the reviews,
BOM.md, PRODUCTION.md's overview) and links to it.

`pcbkit overview` makes it, and the project-overview skill says how. Each round is a small file,
`docs/overview/r<N>.toml`, written from the project's records: the briefing, with every item naming its source.
The command draws each board's turntable and layers, lays out the page, and keeps each round's pictures in
`docs/overview/img/` as they were when it was first built. `pcbkit overview new` starts the next round from the
last; an earlier round only gains notes (`pcbkit overview note`), and `pcbkit overview --check` says when one was
edited, when a source is missing and when the page is not what the rounds say. The marks are done, in work, not
started, needs attention, blocked and your decision, each followed by the project's own word for the state.
`pcbkit overview --single` writes a copy with its pictures inside, to send or publish.

## Scripting rules

- Scripts that touch `pcbnew` run under KiCad's Python and stay 3.9-compatible.
- `pcbkit link` makes the kit importable from KiCad's Python and the `python3` on PATH, but `python3` varies per
  directory on a machine with asdf, direnv or a PlatformIO venv. Every project entry script that imports pcbkit
  therefore starts with the fallback, so it runs under any interpreter:

  ```python
  try:
      import pcbkit  # noqa: F401
  except ImportError:  # an interpreter pcbkit is not linked into: use the checkout
      sys.path.insert(0, os.path.expanduser(os.environ.get("PCBKIT_ROOT", "~/src/pcb-kit")))
  ```
- Once a board is routed, never regenerate it from scratch: update incrementally and keep UUIDs.
- Lock copper that was placed deliberately (power necks, stitching vias); autorouters and cleanups leave locked
  items alone.
- A `.kicad_dru` syntax error silently disables every custom rule; run DRC after each edit of it.
- `BOARD.Remove()` on tracks, drawings or zones and `FOOTPRINT.Remove(field)` corrupt the pcbnew bindings mid-run:
  edit the file text instead (by uuid, or by top-level block as `pcbkit.mech.strip_template` does), in a fresh process.
